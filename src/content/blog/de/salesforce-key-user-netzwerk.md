Key User sind Fachanwender, die das neue Salesforce-System vor allen anderen kennen, an den Tests mitwirken und nach dem Go-live die erste Anlaufstelle für Fragen in ihrem Team sind. Sie tragen außerdem Rückmeldungen aus dem Alltag zurück ins Projekt. Ohne sie geht jede Frage an das Projektteam oder den Support, und viele Fragen werden gar nicht gestellt, sondern mit einer Excel-Liste umgangen. Gute Key User wählt man nach Ansehen im Team aus, nicht nach freier Zeit. Als Planungswert für Workshops, Abnahmetest und die ersten Wochen nach dem Go-live rechne ich mit rund acht Arbeitstagen je Key User, und die gehören vorher in die Planung des Fachbereichs.

## Key User stärken vor allem Wissen und Fähigkeit

Im [ADKAR-Modell](/blog/change-management-salesforce-einfuehrung/) tragen Key User vor allem zu zwei Stufen bei: Wissen (Knowledge) und Fähigkeit (Ability). Je nach Auswahl fördern sie auch die Bereitschaft und helfen, die neue Arbeitsweise nach dem Go-live zu halten. Sponsor und Führung ersetzen sie aber nicht. Eine Schulung vermittelt Wissen, aber erst im Alltag zeigt sich, ob jemand die Funktion im Kundentermin oder am Telefon anwenden kann. In diesem Moment hilft keine Hotline, sondern die Kollegin am Nachbartisch, die es schon einmal gemacht hat.

Bei Herstellern kommt noch etwas hinzu: Vertrieb, Innendienst und Service arbeiten in jedem Land und an jedem Standort ein wenig anders. Das Projektteam kennt diese Unterschiede nicht. Key User kennen sie und können früh sagen, wo der geplante Prozess im eigenen Team nicht funktionieren wird.

```praxis
Beim weltweiten Manufacturing-Cloud-Rollout hatte jedes Land eigene Key User, die das Template kannten und vor Ort die ersten Fragen beantworteten. In Field-Service-Einführungen hilft es, wenn Disponenten der nächsten Welle vorher in einer Region zuschauen, in der das System bereits genutzt wird. Sie lernen dort mehr als in jeder Schulung, weil sie echte Fälle aus ihrem eigenen Alltag sehen.
```

## Die Aufgaben ändern sich mit der Projektphase

So sieht die Rolle in den einzelnen Phasen aus:

```schritte
Vor dem Bau | Workshops · Key User mit Product Owner
  Abläufe im eigenen Team beschreiben, Sonderfälle nennen, Akzeptanzkriterien für User Stories mitformulieren.
Vor dem Go-live | Tests · Key User
  Im Abnahmetest die eigenen Fälle durchspielen und Kollegen in kurzen Sitzungen am echten Fall zeigen, was sich ändert.
Erste Wochen | Alltag · Key User vor Ort
  Erste Anlaufstelle für Fragen, Probleme sammeln und gebündelt ans Projekt melden.
Betrieb | laufend · Key User und Admin
  Neue Kollegen einarbeiten, vor jedem Release erfahren, was sich ändert, und es im Team weitergeben.
```

Key User gehören in den Abnahmetest, weil sie wissen, welche Fälle und Ausnahmen in ihrem Team vorkommen. Sie prüfen vorab festgelegte Abläufe von Anfang bis Ende mit realistischen Daten; die formale Freigabe bleibt bei den benannten Fachverantwortlichen. Wie UAT aufgebaut sein sollte, beschreibe ich in [Salesforce UAT: Wer testet vor dem Release?](/blog/salesforce-uat-abnahmetest-fachbereich/).

## Wie wählen Sie die richtigen Key User aus?

Die häufigste Auswahlmethode ist die schlechteste: Wer gerade Zeit hat, wird Key User. Das sind selten die Personen, die das Team bei Fragen ohnehin anspricht. Ich achte auf andere Kriterien:

- **Ansehen im Team.** Kollegen fragen diese Person schon heute um Rat, unabhängig vom System.
- **Kenntnis des Prozesses.** Sie weiß, wie ein Angebot, ein Auftrag oder ein Serviceeinsatz im eigenen Team abläuft, inklusive der Ausnahmen.
- **Neugier statt Begeisterung.** Ein Key User muss nicht von Salesforce begeistert sein. Kritische Key User finden die Schwächen früher, und wenn sie überzeugt sind, überzeugen sie andere.
- **Bleibt eine Weile.** Wer in drei Monaten die Stelle wechselt, nimmt das Wissen mit.

Planen Sie das Netzwerk nicht pauschal nach Ländern, sondern so, dass jede wichtige Kombination aus Prozess, Rolle, Standort oder Sprache und Rollout-Welle abgedeckt ist. Für kritische Bereiche planen Sie eine Vertretung ein. Fällt der einzige Key User eines Landes in der Woche nach dem Go-live aus, steht das ganze Land ohne Unterstützung da.

## Was ist ein Key User nicht?

Ein Key User ersetzt weder den Support noch den Admin. Der Key User vertritt die fachliche Sicht seines Bereichs, während der Admin die Plattform betreibt und sich um Benutzer, Berechtigungen, Konfiguration und Releases kümmert. Der Key User beantwortet Fragen zur Nutzung, ändert aber keine Konfiguration und behebt keine Fehler in Schnittstellen. Fehler werden weiterhin über das Ticketsystem gemeldet, damit sie gezählt und priorisiert werden. Auch das Schulungsprogramm sollte nicht allein auf ihm liegen: Kurze Einweisungen und Sprechstunden am echten Fall passen gut zur Rolle, Planung und Durchführung ganzer Schulungen nicht. Ohne diese Grenzen ist die Rolle nach wenigen Wochen überlastet, und der Key User hört auf, Fragen zu beantworten.

## Wie viel Zeit muss der Fachbereich freistellen?

Ein Key User ohne freigestellte Zeit ist ein Titel. In der Phase vor und kurz nach dem Go-live braucht die Rolle deutlich mehr Zeit als im Betrieb, weil Workshops, Tests und die ersten Wochen mit vielen Fragen zusammenfallen. Wie viel genau, hängt vom Umfang der Einführung ab. Als Annahme für die Planung: vier Workshops zu je vier Stunden, eine Woche Abnahmetest mit halber Arbeitszeit und zwei Wochen nach dem Go-live mit einem Drittel ergeben zusammen knapp acht Arbeitstage. Dazu kommen Vorbereitung und kurze Sitzungen mit Kollegen. Im Betrieb sinkt der Aufwand auf wenige Stunden im Monat, vor allem rund um Releases.

Diese Zeit muss die Führungskraft vor dem Projektstart zusagen, und jemand muss in dieser Zeit seine Arbeit übernehmen. Sonst testet der Key User nebenbei, und die ersten Fragen nach dem Go-live bleiben liegen, weil das Tagesgeschäft vorgeht.

```hinweis tipp
Vereinbaren Sie die Zeit der Key User schriftlich mit der Führungskraft, einschließlich Wochen und Stunden, und legen Sie fest, wer in dieser Zeit die Arbeit der Key User übernimmt. Diese Vereinbarung ist Teil des Sponsor-Plans.
```

## Das Netzwerk braucht einen festen Termin

Ein Netzwerk aus Key Usern lebt von regelmäßigen Treffen. Ich empfehle einen kurzen Austausch, in dem Key User ihre wichtigsten Rückmeldungen einbringen und vorab erfahren, was das nächste Release ändert. So wird jeder Key User zum Kanal in beide Richtungen: Änderungen gelangen über ihn ins Team, und Probleme aus dem Team gelangen über ihn ins Projekt. Wie dieser Weg vor einem Release aussieht, beschreibe ich in [Salesforce-Releases an den Fachbereich kommunizieren](/blog/salesforce-releases-fachbereich-kommunizieren/).

Wichtig ist auch, dass die Rolle sichtbar anerkannt wird. Wer zusätzliche Arbeit für das Projekt übernimmt, sollte diese Arbeit im Jahresgespräch und in angepassten Tageszielen wiederfinden. Das entscheidet darüber, ob sich beim nächsten Projekt wieder jemand meldet.

## Fragen, wen das Team heute um Rat bittet

Fragen Sie in jedem betroffenen Team: Wen fragen Sie heute, wenn Sie im System nicht weiterkommen? Die Namen, die mehrfach fallen, sind Ihre Kandidaten. Danach vereinbaren Sie mit den Führungskräften die Zeitbudgets und nehmen die Key User in die ersten Workshops mit, bevor die Umsetzung beginnt. Fällt in einem Team kein Name, fühlt sich dort noch niemand für das Thema verantwortlich, und dieses Team braucht in der Schulung mehr Begleitung.
