If your Salesforce implementation partner uses AI agents to write code, check the contract for AI coding rules that a classic SOW rarely covers: which tools and model routes are used, what data may reach the model, no production access for agents, the same review and security gates for every line, and who holds the rights to code generated by a machine. I would not ban AI coding. I would make the partner disclose how it works and make that checkable. For a manufacturer, the sensitive issue is what an agent can read: service cases, dealer prices and SAP credentials.

```hinweis achtung
I am an architect, not a lawyer. The points below describe what I check from the technical side and want to see in writing. They are not legal advice. Your legal department or a lawyer should turn them into clauses that fit your framework agreement.
```

## Why does AI coding by partners need its own clauses?

A classic SOW covers deliverables, acceptance, rights and confidentiality. It quietly assumes that the partner's people wrote the code on the partner's machines. With a coding agent, three things change.

**Data leaves through a new channel.** Files, metadata and tool results that the agent adds to the model context are sent to the configured model provider; the exact flow depends on the tool, provider and gateway. Whether that provider trains on it depends on the contract type, not on the tool. Anthropic states that it [does not train on code or prompts sent to Claude Code under commercial terms](https://code.claude.com/docs/en/data-usage) (Team, Enterprise, API), while on the consumer plans Free, Pro and Max training depends on a user setting. Commercial accounts have a standard retention of 30 days. On top of that, Claude Code keeps session transcripts locally in plaintext for 30 days by default. A developer laptop therefore holds a copy of whatever the agent read.

**Code volume grows faster than review capacity.** Veracode's 2026 report measured the [security pass rate of AI-generated code](https://www.veracode.com/news/llms-are-getting-smarter-but-not-safer-veracode-2026-genai-code-security-report-finds-ai-generated-code-security-has-stalled-at-56%25-pass-rate/). The tests ran against more than 100 raw models, without security prompts, tooling or human review. Apex was not part of the tests, and Java's result says nothing reliable about Apex, which has its own runtime and security model. The conclusion still holds: review plus automated security checks are the control, so both belong in the contract.

```kennzahlen
56 % | Average security pass rate for AI-generated code
30 % | Pass rate for Java in the same tests (Apex was not tested)
source: Veracode, GenAI Code Security Report 2026
```

**Rights get blurry.** [CMS](https://cms.law/de/deu/legal-updates/ki-generierter-softwarecode-in-der-due-diligence) takes the view that code generated entirely without a human contribution is not protected by German copyright law, because only a human can be an author, and a provider's terms cannot change that. Whether a deliverable meets that test depends on the facts, and third-party rights can still apply. And the provider's commitments apply to its own customer. Anthropic's [Commercial Terms](https://www.anthropic.com/legal/commercial-terms) (effective June 17, 2025) defend the customer that signed them, and exclude claims arising from modified output, output combined with technology or content not provided by Anthropic, or the customer's own inputs. Code in a Salesforce org is almost always modified and combined. If the partner holds the account, that customer is the partner, not you.

## Which AI coding rules belong in the partner contract?

I use these nine items as a checklist for SOWs and framework agreements. Not every program needs all of them in the same depth.

1. **Disclosure of tools and model routes.** The partner names each coding tool, the model provider, the route (direct API, cloud provider or a Salesforce tool such as Agentforce Vibes) and the contract type. Changes are announced before use. The route decides where data is processed: Anthropic's first-party API offers only ["us" or "global" as inference region](https://platform.claude.com/docs/en/manage-claude/data-residency), while on Amazon Bedrock the region follows the endpoint. OpenAI introduced [European data residency](https://openai.com/index/introducing-data-residency-in-europe/) in February 2025 for eligible endpoints in newly created API projects, so the partner should document project region, endpoint and retention setting.
2. **Commercial accounts only.** No private Pro or Max accounts in a client project. If you provide the licenses yourself, you also set the policy, as described in [why clients should own their DevOps tools](/en/blog/why-clients-should-own-their-devops-tools/). Who pays for the tokens is a separate negotiation, covered in [AI coding costs in a Salesforce project](/en/blog/ai-coding-costs-salesforce-project/).
3. **Data classes for the agent context.** Code and metadata may reach the model after a scan or review confirms that they contain no personal data, secrets or confidential logic outside the agreed class; metadata also contains user names, endpoints and price logic. Production data, personal data, dealer price lists, conditions and customer data from service cases may not reach the model. The org type is not an effective control: a developer sandbox copies metadata, not records, but can be filled with real data afterwards. Agents work with synthetic or documented masked data, checked after every refresh. A full copy sandbox contains a copy of production data. If the partner processes personal data on your behalf, the contract also names the processing chain: subprocessors including the model provider, processing countries, transfer mechanism, deletion periods and incident reporting.
4. **No production access for agents.** Deployments to production go through the pipeline with a human approval. Salesforce lets you [disable Agentforce Vibes for a production org](https://developer.salesforce.com/blogs/2025/12/five-pro-tips-for-using-agentforce-vibes) in Setup, but that only stops Vibes when production is the default org. It does not stop other AI tools, the Salesforce CLI or MCP servers. The local [Salesforce DX MCP Server](https://developer.salesforce.com/docs/platform/sfdx-dev/guide/sfdx-dev-mcp.html), which could access only explicitly allowlisted orgs, reached end of life on November 2, 2026; see [the DX MCP Server end of life](/en/blog/salesforce-dx-mcp-server-end-of-life/). What actually enforces the rule: no production credentials on developer machines, no production org in agent or MCP configurations, separate technical identities and regular checks of the authorized orgs. Credentials such as the SAP integration user stay outside the agent's reach; Anthropic's [secure deployment guide](https://code.claude.com/docs/en/agent-sdk/secure-deployment) describes a proxy that injects them so the agent never sees them.
5. **The same review and gates for every line.** Each pull request has a named human owner and records the tool, the model and how AI was used (generated, modified or only reviewed), and the pipeline gates apply unchanged: Salesforce Code Analyzer, secret scanning, CRUD/FLS and sharing rules, checks for dynamic SOQL and a license scan. Salesforce's own Vibes documentation puts it plainly: ["Permission modes protect your filesystem. Code review protects your application."](https://developer.salesforce.com/docs/platform/agentforcevibes/guide/afv-trust.html) How reviews work is in [why pull request reviews are a must](/en/blog/why-pull-request-reviews-are-a-must-in-enterprise-projects/); what to look for in AI code is in [reviewing AI-generated Salesforce code](/en/blog/reviewing-ai-generated-salesforce-code/).
6. **Rules file in your repository.** Conventions for agents, such as API version, sharing and test standards, are kept in an AI rules file in your repository and apply to every partner. Tools read different file names, so the partner shows that its tool loads them; the binding control remains the pipeline. More in [an AI rules file for the Salesforce repository](/en/blog/ai-rules-file-salesforce-repository/).
7. **Rights and licenses.** The rights clause covers human and AI-generated parts, and the partner documents where AI was used, as CMS recommends for later due diligence. Ask how public code matches are handled: GitHub Copilot can [block suggestions that match public code](https://github.blog/news-insights/product-news/code-referencing-now-generally-available-in-github-copilot-and-with-microsoft-azure-ai/) or show them with license information.
8. **Liability stays where it was.** The partner is responsible for its deliverables, regardless of which tool produced them. Warranty, acceptance criteria and defect handling apply as before, with no exclusion for "generated by AI". CMS warns that provider indemnities often include broad exclusions, so they do not replace the partner's indemnity.
9. **Evidence and exit.** New tools, providers or routes need approval before use. You may ask for the tool list, the account list and relevant settings at the start, at every material change and on reasonable suspicion, and the partner reports leaked credentials or data sent to the wrong place without delay. At the end of the engagement, the partner confirms that local transcripts, caches, cloud sessions and feedback uploads with your code are deleted, or states what must be retained and why.

## Worked example: two partners, one questionnaire

Assume a machinery manufacturer with Sales Cloud, Service Cloud and Field Service in one org, SAP as ERP and two partners. Partner A builds the dealer portal and the service processes with six developers, partner B the SAP integration with three. All details here are assumptions to show the method.

Before extending the SOWs, IT sends both partners a one-page questionnaire: tools, model routes, account types, sandboxes with real data, who holds which credentials. The answers in this scenario:

- Partner A uses a coding agent on a company account, but two developers occasionally switch to private accounts when the company quota runs out.
- Partner A's agent works in a full copy sandbox that contains real service cases with customer names and machine serial numbers.
- Partner B has the password of the SAP integration user in a local file inside the project folder the agent can read.
- Partner B allows suggestions that match public code and has never looked at the license notes.

Only the last finding might show up in a code review or license scan; the other three would not, because the code itself is fine. The fix is a two-page annex to the framework agreement with the nine items above, plus a few weeks to move partner A to a developer sandbox with masked data and to move partner B's credentials into the client's vault. For new SOWs, the annex applies automatically.

## What changes when several partners work on one org?

Agents make changes inexpensive, including changes to objects owned by another stream. An agent that "fixes" a validation rule on Account while working on a dealer portal story has no way of knowing that the service stream depends on it. That makes the [object ownership matrix](/en/blog/salesforce-object-ownership-matrix/) more important. A CODEOWNERS file in the repository automatically requests the owning stream as a reviewer when a pull request touches its objects.

The annex should be identical for all partners. If each partner brings its own AI rules, the strictest or the loudest one quietly becomes your standard, and comparing partners becomes harder. To prevent the rules from fading after a few months, the contract is not enough: they need the pipeline, review and a regular forum for new cases, described in [Reinforcement: making standards stick with partners](/en/blog/partner-standards-reinforcement/). Setting these rules on the client side is part of my work in [partner governance](/en/services/partner-governance/).

## Send a questionnaire to every partner

```schritte
Send the questionnaire
  To every partner, including small ones that only deliver a single integration.
Classify your data
  Into what an agent may see and what it may not, with your data protection officer.
Draft the annex
  With your legal department, attached to the framework agreement so it applies to every SOW.
Enforce it technically
  No production credentials on developer machines, Vibes disabled for production, deployments only through the pipeline, CODEOWNERS for shared objects.
Review it at every change
  Tools, plans and terms change faster than contracts, so a new tool or route triggers a check, plus a yearly review.
```
